1. ## Title: L01: Initializer Function Not Explicitly Protected

### Description:

The initialize function in AgentOwnerRegistry is publicly exposed and lacks an explicit initializer restriction modifier (e.g., OpenZeppelin's initializer). While a re-initialization guard (state.initialised check) exists within the internal initialise function, this deviates from standard patterns and requires auditors and developers to trace the call flow to verify security.

### Recommendation:

For clarity and adherence to best practices, consider using the OpenZeppelin Initializable contract and protect the initialize function with the initializer modifier. This makes the access control explicit and immediately visible.

### Severity:

Low / Informational (There is no immediate risk of funds being lost or protocol logic being broken, but the code quality is suboptimal and could lead to issues in future development.)

2. ## Title: L02: Timelock Extension Attack Vulnerability in GovernedBase

### Description:

The \_recordTimelockedCall function in GovernedBase allows governance to repeatedly extend the timelock for a specific call by re-submitting the same encoded call with a new minimum timelock. This can be exploited by malicious actors with governance control to indefinitely delay the execution of legitimate proposals, effectively preventing them from ever being executed.

### Recommendations:

Fix 1: Prevent Overwriting Existing Timelocks

```js
solidityfunction _recordTimelockedCall(bytes calldata _encodedCall, uint256 _minimumTimelock) private {
    // ...
    bytes32 encodedCallHash = keccak256(_encodedCall);

    // 🔧 FIX: Don't allow overwriting existing timelocks
    require(state.timelockedCalls[encodedCallHash] == 0, "Call already timelocked");

    uint256 allowedAt = block.timestamp + timelock;
    state.timelockedCalls[encodedCallHash] = allowedAt;
    // ...
}
```

Fix 2: Allow Updates Only If Current Timelock Has Passed

```js
function _recordTimelockedCall(bytes calldata _encodedCall, uint256 _minimumTimelock) private {
    // ...
    bytes32 encodedCallHash = keccak256(_encodedCall);
    uint256 existingTimelock = state.timelockedCalls[encodedCallHash];

    // 🔧 FIX: Only allow updates after current timelock expires
    if (existingTimelock != 0) {
        require(block.timestamp >= existingTimelock, "Previous timelock still active");
    }

    uint256 allowedAt = block.timestamp + timelock;
    state.timelockedCalls[encodedCallHash] = allowedAt;
    // ...
}
```

Fix 3: Separate Update/Cancel Functions

```js
// Explicit function to update timelocked calls
function updateTimelockedCall(bytes calldata _encodedCall) external onlyImmediateGovernance {
    bytes32 encodedCallHash = keccak256(_encodedCall);
    require(state.timelockedCalls[encodedCallHash] != 0, "No existing timelock");

    // Only allow updates, don't extend timelock
    // Or require special conditions for updates
}
```

3. ## [INFO-01] Inefficient Storage Pattern for Related Agent Data

**Impact:** Informational/Gas Optimization

**Likelihood:** N/A

**Description:**
The contract uses separate mappings for related agent data instead of a struct, leading to:

-   Increased gas costs for batch operations (~25% higher)
-   Code duplication across 4 similar functions
-   Reduced maintainability and extensibility

**Recommendation:**
Consider refactoring to use a single `AgentInfo` struct with a mapping from address to struct.

**Gas Impact:**

-   Current: 4 transactions × ~20k gas = 80k gas
-   Optimized: 1 transaction × ~60k gas = 60k gas
-   Savings: 25% reduction for full updates

```js
struct AgentInfo {
        string name;
        string description;
        string iconUrl;
        string touUrl;
        // Future fields can be added without new mappings
        // uint256 rating;
        // bool isActive;
        // uint256 createdAt;
    }

    mapping(address => AgentInfo) private agentInfo;

    function setAgentInfo(
        address _managementAddress,
        string memory _name,
        string memory _description,
        string memory _iconUrl,
        string memory _touUrl
    ) external onlyGovernanceOrManager {
        AgentInfo storage info = agentInfo[_managementAddress];
        info.name = _name;
        info.description = _description;
        info.iconUrl = _iconUrl;
        info.touUrl = _touUrl;
        emit AgentDataChanged(_managementAddress);
    }

    /**
     * Batch update multiple fields efficiently
     */
    function updateAgentInfo(
        address _managementAddress,
        string memory _name,
        string memory _description,
        string memory _iconUrl,
        string memory _touUrl
    ) external onlyGovernanceOrManager {
        AgentInfo storage info = agentInfo[_managementAddress];

        // Only update non-empty strings
        if (bytes(_name).length > 0) info.name = _name;
        if (bytes(_description).length > 0) info.description = _description;
        if (bytes(_iconUrl).length > 0) info.iconUrl = _iconUrl;
        if (bytes(_touUrl).length > 0) info.touUrl = _touUrl;

        emit AgentDataChanged(_managementAddress);
    }

```

4. ## Title: Work Address Takeover Vulnerability

```js
solidityfunction setWorkAddress(address _ownerWorkAddress) external {
    require(isWhitelisted(msg.sender), AgentNotWhitelisted());
    require(_ownerWorkAddress == address(0) || workToMgmtAddress[_ownerWorkAddress] == address(0),
           WorkAddressInUse());
    // ... rest of function
}
```

### Description:

The setWorkAddress function allows an agent to set or change their work address. However, if an agent is de-whitelisted, they cannot change their work address anymore, leading to a situation where the work address remains permanently locked and unusable.

Scenario:

Agent A sets work address W
Agent A gets de-whitelisted
Agent A cannot call setWorkAddress(address(0)) to free up work address W
Work address W is permanently locked

### Impact:

Work addresses can become permanently unusable.
